# 개발·운영 가이드

[← DAILY TICK 소개로 돌아가기](../README.md)

AI 생성 흐름, 협업 사례, 검증 근거와 로컬 실행 방법을 정리한 문서입니다.

## AI는 어떻게 동작하나요

OpenAI Responses API를 활용해 **뉴스 탐색 → 근거 선택 → 브리핑 작성 → 의미 검토**를 별도의 호출로 수행합니다.
서버는 이 사이에서 실제 기사 본문을 수집하고, 근거를 대조하고, 발행 조건을 검사합니다.

매일 예약 작업으로 브리핑을 미리 생성해 Supabase에 저장하고,
사용자가 페이지에 접속하면 저장된 콘텐츠를 조회합니다. 페이지 조회 시에는 AI를 호출하지 않습니다.

![AI 뉴스 검색부터 원문 수집·근거 대조·작성·발행 검증·저장까지의 흐름](./assets/ai-pipeline.svg)

### AI와 서버가 맡는 역할

| 단계 | AI가 하는 일 | 서버가 확인·처리하는 일 |
| --- | --- | --- |
| 01 · 학습 주제 선정 | 선정된 개념의 설명에 활용 | [커리큘럼](../src/data/curriculum.ts)과 발행 이력으로 오늘의 개념 선택 |
| 02 · 뉴스 탐색 | `web_search`로 최근 국내·글로벌 이슈 탐색 | 완료된 검색·페이지 열기 기록의 URL과 후보 출처 대조 |
| 03 · 본문 확보 | 수집한 본문을 다음 단계의 자료로 사용 | 공개 기사·발표 자료의 HTML에서 본문과 실제 게시 정보 추출 |
| 04 · 근거 선택 | 본문에서 핵심 근거 문장 1~3개 선택 | 출처 ID, 원문 문장 일치, 게시 시각 범위 검사 |
| 05 · 브리핑 작성 | 근거 ID를 선택하고 제목·금융 해설·교육 내용 작성 | 사실 본문과 출처를 검증된 원문에서 조합 |
| 06 · 발행 검토 | 별도 호출로 원문 맥락, 수치·시점, 해설의 근거 검토 | Zod 형식 검사, 뉴스의 새 수치 검사, 검토 누락·중복 확인 |
| 07 · 저장·조회 | — | 통과한 브리핑 저장, 생성·근거 로그 기록, 페이지에 제공 |

오늘의 학습 주제는 **브리핑 발행 이력**을 기준으로 고릅니다.
모든 개념을 다룬 뒤에는 가장 오래전에 등장한 개념부터 복습합니다.

### 발행 전에 확인하는 것

| 상황 | 처리 |
| --- | --- |
| 실제 검색 기록에 없는 URL | 후보 출처에서 제외 |
| 본문에 없는 문장이나 잘못된 근거 ID | 근거 선택·본문 조합 단계에서 거절 |
| 선택한 근거에 없는 숫자 | 뉴스 제목·해설의 수치 검사에서 차단 |
| 과거 사건을 현재 사건으로 설명 | 원문 맥락을 전달한 AI 의미 검토에서 평가 |
| 검토 결과 누락·중복 또는 API 장애 | 발행 차단 |
| 내용 검증 실패 | 위반 내용을 전달해 1회 수정 재시도 |
| 최종 생성 실패 | 기존 브리핑 보존, 확보한 근거와 실패 단계 기록 |

**AI 의미 검토도 모델의 판단입니다.** 서버의 원문 일치 검사에 더하는 발행 조건이며,
모든 사실 오류를 검출한다고 보장하지 않습니다.

구현은 [생성 흐름](../src/lib/briefing/create-daily-briefing.ts),
[뉴스 수집](../src/lib/openai/collect-news.ts), [근거 확보](../src/lib/openai/ground-news.ts),
[원문 조합](../src/lib/briefing/materialize.ts), [발행 검토](../src/lib/news/review.ts)에서 확인할 수 있습니다.

## AI와 어떻게 협업하나요

**개발자가 서비스의 목표와 우선순위를 정하고, AI 코딩 도구(Codex)와 함께 구현·리뷰·검증을 진행합니다.**
프론트엔드 화면부터 서버 API, 데이터 저장, 뉴스 검증 흐름까지 연결해서 작업하며,
변경한 코드와 재현 결과를 근거로 다음 개선 방향을 정합니다.

> 문제 정의 → 설계 검토 → 구현 → 오류 재현·테스트 → 결과 기록 → 다음 개선

### 협업에서의 역할 분담

| 작업 | 개발자 | AI 코딩 도구 |
| --- | --- | --- |
| 문제 정의 | 사용자에게 필요한 경험과 작업 우선순위 설정 | 현재 코드 파악, 요구사항과 확인할 조건 구체화 |
| 설계 검토 | 기능 범위와 제안된 방법 검토 | 구현 대안, 데이터 흐름, 예상 실패 상황 설명 |
| 구현 | 결과를 확인하고 요구사항 보완 | 화면·API·DB 로직 구현과 관련 문서 수정 |
| 검증 | 확인된 결과와 남은 문제를 보고 다음 작업 결정 | 코드 리뷰, 문제 재현, 테스트 실행과 결과 정리 |
| 기록 | 공개할 내용과 설명 검토 | 변경 이유, 검증 근거, 한계를 코드·커밋과 연결해 정리 |

### 로컬 실행

#### 1. 환경 준비

Node.js **22.15 이상**에서 실행합니다. 저장소 루트에서 의존성과 환경변수를 준비합니다.

```bash
npm ci
cp .env.example .env.local
```

[.env.example](../.env.example)을 기준으로 `.env.local`에 값을 입력합니다.

| 환경변수 | 용도 |
| --- | --- |
| `OPENAI_API_KEY` | 뉴스 검색·생성·검토 API 키 |
| `OPENAI_MODEL` | 사용할 모델. 기본값은 `.env.example` 참고 |
| `SUPABASE_URL` | Supabase 프로젝트 URL. `/rest/v1` 경로 제외 |
| `SUPABASE_SERVICE_ROLE_KEY` | 서버 전용 데이터베이스 접근 키 |
| `CRON_SECRET` | 브리핑 생성 API의 Bearer 인증 값 |
| `NEXT_PUBLIC_SITE_URL` | 서비스 기준 URL. 로컬은 `http://localhost:3000` |
| `AUTH_ID` · `AUTH_PASSWORD` · `AUTH_SECRET` | 학습 기록용 로그인 설정. 비밀번호 8자 이상, 서명 키 32자 이상 |

환경변수는 실제 사용 시 Zod로 검사합니다. 로그인 설정은 브리핑 생성 설정과 분리되어 있습니다.

#### 2. 데이터베이스 준비

새 Supabase 프로젝트에서는 SQL Editor에서 [schema.sql](../supabase/schema.sql)을 실행합니다.
기존 프로젝트에서 근거 로그를 추가하려면
[20261009_news_evidence_audit.sql](../supabase/migrations/20261009_news_evidence_audit.sql)을 적용합니다.

마이그레이션 전에는 기본 생성 로그만 저장할 수 있습니다.
기존 형식의 브리핑도 계속 읽을 수 있으며, 과거 데이터의 자동 변환은 수행하지 않습니다.

#### 3. 개발·검증

```bash
npm run dev
```

```bash
npm test
npm run lint
npm run build
```

테스트는 외부 API·DB 쓰기 없이 실행되며, 실제 브리핑 생성은 다음 단계에서 별도로 실행합니다.

#### 4. 브리핑 수동 생성

개발 서버를 실행하고, **호출할 터미널에도 `CRON_SECRET`을 설정**한 뒤 요청합니다.
`.env.local`은 Next.js가 읽으며 셸 환경변수로 자동 등록되지 않습니다.

```bash
curl -X POST "http://localhost:3000/api/cron/daily-briefing" \
  -H "Authorization: Bearer $CRON_SECRET"
```

| 쿼리 파라미터 | 동작 |
| --- | --- |
| 생략 | 오늘의 KST 날짜로 생성. 이미 있으면 기존 브리핑 반환 |
| `?date=YYYY-MM-DD` | 지정한 날짜로 생성 |
| `?force=true` | 검증을 통과한 새 결과로 기존 브리핑 교체 |

### 데이터와 운영

| 테이블 | 저장 내용 |
| --- | --- |
| `briefings` | 날짜별 뉴스·금융 개념, 키워드, 한 줄 요약, 모델·프롬프트 버전, 뉴스별 근거 |
| `generation_logs` | 실행 상태, 토큰·검색 호출 수, 시도 횟수, 위반 내용, 실패 단계, 근거·검토 기록 |
| `study_logs` | 날짜별 학습 완료 시각과 메모 |

근거 로그에는 검색 기록, 채택·탈락 이유, 짧은 근거 문장, URL, 수집 시각과 본문 hash를 남깁니다.
원문 전체는 로그에 복제하지 않습니다. 프롬프트는 [prompts.ts](../src/lib/openai/prompts.ts)에서 관리하고,
브리핑에 `PROMPT_VERSION`을 저장해 변경 이력을 추적합니다.

`briefing_date`의 UNIQUE 제약으로 날짜당 저장 행은 하나로 유지합니다.
이미 발행된 날짜는 일반 생성 요청에서 재사용하며, 동시 요청의 실행 잠금은 후속 개선 과제입니다.

Vercel Cron 설정은 **UTC 22:30 / KST 다음 날 07:30**이며, 목표 발행 시각은 **08:30 KST**입니다.
서비스 날짜는 `Asia/Seoul` 기준으로 계산합니다.

#### 반복되는 검증 위반 조회

재시도로 성공한 실행에도 최초 위반 내용을 남겨 자주 실패하는 검증 항목을 조회할 수 있습니다.

```sql
select v->>'code' as code, count(*)
from generation_logs, jsonb_array_elements(violations) v
group by 1
order by 2 desc;
```

### 수집 범위와 실행 제한

- 공개 HTTPS HTML의 기사·발표 본문을 지원합니다. PDF/HWP, JavaScript로만 표시되는 본문,
  로그인·유료 자료, 게시 정보를 확인할 수 없는 자료는 발행 근거에서 제외합니다.
- 후보당 최대 3개 출처를 확인하며, 최신 본문을 처음 확보하면 다음 단계로 넘깁니다.
- 출처 요청은 10초, 1.5MB, 리다이렉트 3회로 제한합니다.
- DNS로 확인한 공인 IPv4에 연결하며 내부 주소, IP 직접 입력, 비표준 포트, IPv6-only 출처를 제한합니다.
- 최대 10개 후보를 3개씩 처리합니다. AI에 전달하는 본문은 자료당 12,000자로 제한합니다.
